# AntiBlock load and stress tests

This suite complements `tests/integration/`. The integration suite answers whether AntiBlock is
correct; this suite measures end-to-end load behavior and keeps the same real libpcap/Linux routing
path under sustained traffic.

The hot path is generated by the C projects `dns-client-test` and `dns-server-test`. Python only
orchestrates runs, prepares workload files, reads counters, and checks results. Python is not the DNS
load generator.

## Quick start

Download a Cloudflare Radar Top 1M CSV and run:

```sh
./tests/load/run.sh cloudflare-radar_top-1000000-domains_YYYYMMDD-YYYYMMDD.csv
```

Optional modes:

```sh
./tests/load/run.sh cloudflare-radar_top-1000000-domains_YYYYMMDD-YYYYMMDD.csv performance
./tests/load/run.sh cloudflare-radar_top-1000000-domains_YYYYMMDD-YYYYMMDD.csv stress
```

The CSV itself and generated replay cache are not committed to the repository. The load image uses
Docker build cache by default, so repeated benchmark runs do not reinstall the toolchain or pull the base
image when only local sources changed. Use `LOAD_NO_CACHE=1` for a deliberately clean rebuild with
`--pull --no-cache`.

## One-time DNS replay-cache preparation

AntiBlock always loads the complete normalized Cloudflare list, so the domain hashmap contains the
full dataset (normally about one million domains).

A replay server does not need a real response for every one of those domains. By default the setup asks the updated `dns-client-test` to select a reproducible 100,000-domain sample with `-n 100000 --seed 701184`, explicitly uses A mode (`-A`), and queries the upstream resolver at 250 requests per second:

```text
Cloudflare Top 1M CSV
        |
        +--> domains.txt             full table loaded by AntiBlock
        |
        |
        v
 dns-client-test -A -n 100000 --seed 701184
        |
 1.1.1.1:53 @ 250 RPS
        |
        v
   cache-A.data
   out_domains-A.txt
```

At 250 RPS, 100,000 requests require about 6 minutes 40 seconds before DNS latency/timeouts. This is
only a preparation step. It is skipped on later runs while the normalized dataset, upstream address, sample size, seed, and checked-out `dns-client-test` commit match the saved cache key.

The default is deliberately conservative. It is not an assertion that 500 RPS is an official Cloudflare limit. `PREP_SAMPLE`, `PREP_RPS`, and `PREP_SEED` are passed directly to the current client interface. Override when appropriate:

```sh
PREP_RPS=400 PREP_SAMPLE=200000 PREP_SEED=12345 ./tests/load/run.sh cloudflare.csv
```

To collect responses for the entire million-domain file:

```sh
PREP_SAMPLE=1000000 ./tests/load/run.sh cloudflare.csv
```

All measured performance/stress traffic after cache preparation is local Docker traffic and does not
query Cloudflare or any other public resolver.

## Local topology

`run.sh` creates an isolated Docker bridge and starts `dns-server-test` in a separate container at a
fixed private address. The runner container contains `dns-client-test` and AntiBlock:

```text
dns-client-test (C)
        |
        | UDP queries
        v
Docker bridge
        |
        v
dns-server-test (C, -c cache-A.data)
        |
        | UDP responses
        v
Docker bridge -> libpcap(any) -> AntiBlock
                               -> DNS parser
                               -> 1M domain hashmap
                               -> blacklist / CNAME / HTTPS AliasMode logic
                               -> route state
                               -> Linux route ioctl when enabled
```

The containers use `NET_ADMIN` and `NET_RAW`, not `--privileged` or host networking. Routes created by
the route tests exist only in the disposable runner network namespace.

The current `dns-client-test` names A-mode artifacts `cache-A.data` and `out_domains-A.txt`. The load runner therefore starts the updated `dns-server-test` with `-c /work/cache-A.data`; it no longer relies on the legacy implicit `cache.data` filename.

## Capture-loop behavior

AntiBlock keeps libpcap in non-blocking mode so periodic TTL expiration, statistics and domain reload
work do not depend on incoming traffic. When `pcap_next_ex()` reports that no packet is immediately
available, the main loop now waits with `poll()` on libpcap's selectable descriptor instead of doing
a blind fixed sleep. A packet therefore wakes the process immediately, while the bounded poll timeout
still gives the maintenance loop regular opportunities to run.

This matters for burst traffic: a fixed sleep after an empty non-blocking read can leave packets in the
kernel capture queue unnecessarily and can turn the sleep interval into artificial benchmark loss.

## Four scenarios

### Test 1: release DNS throughput

GCC Release AntiBlock is tested with the full domain table.

It first runs a cold lookup sweep across distinct cached domains. All IPv4 results are intentionally
blacklisted with two `/1` ranges, so this phase can traverse many different domains without filling
the intentionally bounded 1024-entry live-route state.

It then runs a small repeated hot set with `--test`. That phase leaves kernel route ioctls disabled
but keeps userspace route-state lookup/update enabled. The configured rate is increased through the
QPS steps, while the report also shows the actual peak response rate observed by `dns-client-test`.
This prevents a client/server generator ceiling from being mistaken for an AntiBlock ceiling.

AntiBlock also exports libpcap `ps_recv`, `ps_drop` and `ps_ifdrop` counters into `stat.txt`. The load
report prints those counters together with processed packet ratio, AntiBlock CPU time and peak RSS.
A successful high-rate step therefore distinguishes application processing from kernel capture loss.

No hard performance number is a pass/fail requirement because machines differ. Process survival,
valid parsing, and a non-full route state are correctness requirements.

### Test 2: release real kernel route programming

AntiBlock runs without `--test` and receives a bounded set of cached domains. Real `/32` routes are
installed through `lo` using the normal `SIOCADDRT` path. The script watches `/proc/net/route` for the
whole client run, records the highest AntiBlock-owned route count and the time when that peak was
reached, then keeps a short settle window for packets already buffered in libpcap/AntiBlock. The
reported rate is based on time-to-peak, not on the client's later receive-tail delay. After each cycle
AntiBlock is terminated and metric-23117 routes must be completely cleaned up.

This workload is intentionally bounded because AntiBlock itself has a 1024-entry live route-state
capacity. The benchmark measures the real configured product behavior rather than changing that
limit for a benchmark-only build.

### Test 3: Clang ASan + UBSan DNS stress

The sanitizer build loads the full domain table and processes a long high-rate replay workload.
Routes are blacklisted in this phase so the stress remains focused on capture, DNS parsing, alias propagation, and domain-table work without overflowing the bounded route table.

The test fails on an AntiBlock crash, parser errors, ASan diagnostics, or UBSan diagnostics.
Throughput and libpcap drop counters are printed for information only and are not compared with the
Release result.

### Test 4: Clang ASan + UBSan real-route churn

The sanitizer build repeatedly starts AntiBlock, installs real kernel routes from DNS answers, then
stops it and verifies complete route cleanup. Repeating add/cleanup cycles stresses the userspace
route hashmap, kernel route ioctls, shutdown path, and ownership metric under sanitizers.

## Main tuning variables

Defaults are chosen to keep the suite useful on a normal development machine while making the
workload easy to increase:

```text
PREP_SAMPLE=100000
PREP_RPS=250
PREP_SEED=701184
UPSTREAM_DNS=1.1.1.1:53

LOAD_RATES="10000 25000 50000 100000 200000 400000"
LOAD_REQUESTS=200000
COLD_REQUESTS=50000
COLD_RPS=50000
HOT_SET_SIZE=32
ZERO_LOSS_PERCENT=99.5

ROUTE_QUERY_COUNT=256
ROUTE_CYCLES=5
ROUTE_RPS=100000

STRESS_REQUESTS=500000
STRESS_RPS=50000
ROUTE_STRESS_QUERY_COUNT=128
ROUTE_STRESS_CYCLES=10
ROUTE_STRESS_RPS=20000
```

Example heavier stress run:

```sh
STRESS_REQUESTS=2000000 STRESS_RPS=100000 \
ROUTE_STRESS_CYCLES=50 \
./tests/load/run.sh cloudflare.csv stress
```

## Tool revisions

The Docker build clones:

- `https://github.com/karen07/dns-client-test`;
- `https://github.com/karen07/dns-server-test`.

The default ref for each is `main`, and the exact checked-out commit hashes are printed by the test
runner. A release/CI job can pin them explicitly:

```sh
DNS_CLIENT_REF=<commit> DNS_SERVER_REF=<commit> \
./tests/load/run.sh cloudflare.csv
```

This keeps local development convenient while making a published benchmark reproducible when exact
refs are supplied.
