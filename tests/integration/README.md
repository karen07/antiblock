# AntiBlock Integration Tests

Docker-based end-to-end tests for AntiBlock covering DNS parsing, domain matching, dynamic Linux routes, and memory safety across GCC, Clang, and sanitizer builds.

## Описание

Интеграционные end-to-end тесты AntiBlock в Docker проверяют разбор DNS, сопоставление доменов, динамические маршруты Linux и безопасность работы с памятью в сборках GCC, Clang и с санитайзерами.

Тестовый стенд собирает AntiBlock из исходников внутри `archlinux:latest`. Один набор Python-тестов выполняется с тремя бинарными файлами: GCC Release, Clang Release и Clang с AddressSanitizer + UndefinedBehaviorSanitizer. Проверяется реальный путь от DNS-пакета через libpcap и AntiBlock до таблицы маршрутизации ядра, а не только отдельные функции парсера.

## Требования

- Docker с работающим демоном и возможностью получить `archlinux:latest` при первой сборке.
- Права контейнеров `NET_ADMIN` и `NET_RAW` для работы с маршрутами и сетевыми пакетами.
- Не требуются `--privileged` и `--network host`: маршруты остаются в сетевом пространстве имён контейнера.

## Быстрый старт

Из корня репозитория AntiBlock:

```sh
./tests/integration/run.sh
```

Для полной пересборки, включая обновление базового образа:

```sh
INTEGRATION_NO_CACHE=1 ./tests/integration/run.sh
```

По умолчанию используется кеш слоёв Docker, поэтому повторные запуски при изменении исходников не переустанавливают весь инструментарий Arch Linux.

## Архитектура и реализация

### Модель тестирования

```text
fake DNS server
      |
      v
UDP DNS response
      |
      v
real libpcap capture
      |
      v
AntiBlock DNS/domain/alias logic
      |
      v
real Linux routing table
```

HTTP connect/total timeouts в тестовых сборках сокращены до 1/2 секунд, чтобы быстро воспроизводить ошибки зависшего HTTP-источника. Штатные значения для production - 5/30 секунд.

## Тестирование

### Охват функциональных сценариев

Набор включает проверки:

- маршрутизации для прямой A-записи и отсутствия маршрута для неподходящего домена;
- встроенных и пользовательских CIDR blacklist;
- CNAME и A в одном ответе, а также запоминания CNAME для последующих независимых ответов;
- независимости времени жизни выученного CNAME от TTL записи CNAME;
- сопоставления поддоменов цели CNAME, нескольких переходов CNAME и независимости обработки от порядка RR;
- обучения цели HTTPS AliasMode (`TYPE 65`, `SvcPriority=0`) и смешанных цепочек CNAME + HTTPS AliasMode независимо от порядка RR;
- исключения HTTPS ServiceMode из механизма алиасов;
- истечения TTL маршрута, игнорирования `TTL=0`, продления TTL для того же правила и защиты от более короткого TTL;
- перемещения адреса между правилами и применения TTL нового правила;
- маршрутов через L2-интерфейс с обнаруженным default gateway, выбора шлюза с минимальной метрикой и корректного отказа при отсутствии шлюза;
- маршрутов для L3-интерфейсов;
- регистра DNS без учёта регистра символов, поддоменов, точных правил `!domain`, нормализации `www.` / `WWW.` и разбора CRLF;
- пустого первого списка доменов с последующим непустым источником под UBSan;
- `--test` без изменений таблицы маршрутов ядра;
- создания `--log` и `--stat`;
- загрузки доменов через HTTP, обработки сбоя HTTP и восстановления после повтора с тестовым интервалом 2 секунды;
- нулевого размера write callback libcurl (отдельный санитайзерный unit-тест);
- общего таймаута зависшего HTTP-сервера без блокирования последующих локальных списков;
- очистки маршрутов по SIGTERM и SIGINT;
- повторяющихся 16-битных DNS transaction ID;
- очистки на старте только маршрутов, принадлежащих AntiBlock по метрике;
- отображения версии/справки и обработки корректного DNS-ответа с дополнительной OPT-секцией.

Одни и те же **61 тест** проходят на трёх сборках: успешный полный запуск даёт **183 end-to-end выполнения**.

### Регрессии некорректных DNS-пакетов

Негативные сценарии формируются на Python, но намеренно проходят через настоящий UDP/libpcap-путь и C-парсер AntiBlock. Для каждого пакета проверяется, что процесс жив, ошибочный маршрут не появился, а следующий корректный ответ обрабатывается.

Проверяются:

1. Обрезанный DNS header.
1. Отсутствующий флаг response.
1. Некорректное число Questions.
1. Указатель сжатия имени за пределы пакета.
1. Цикл в указателях сжатия.
1. Обрезанная фиксированная часть Question.
1. DNS label, выходящий за пределы пакета.
1. Отсутствующий второй байт compression pointer.
1. Обрезанный заголовок RR.
1. Обрезанное имя владельца Answer / compression pointer.
1. RDATA за пределами пакета.
1. Неверный RDLENGTH A-записи.
1. Указатель сжатия CNAME за пределы пакета.
1. Имя CNAME, занимающее не ровно RDLENGTH.
1. Обрезанная метка имени CNAME target.
1. Сжатый HTTPS AliasMode TargetName, запрещённый RFC 9460.
1. Зарезервированный или некорректный формат DNS label.
1. Декодированное DNS-имя, превышающее размер выходного буфера парсера.

Сборка ASan + UBSan помогает выявлять регрессии безопасности памяти и неопределённого поведения.

### Отличие от тестов AntiBlock 2.x

В AntiBlock 2.x использовалась большая внутрипроцессная функция `dns_ans_check_test()`, обращавшаяся к закрытым функциям парсера и проверявшая внутренние коды возврата. В AntiBlock 3.0.0 этого внутреннего API нет; протокольные сценарии перенесены в E2E-тесты Python.

Сценарии, привязанные только к старому `memory_t.max_size`, заменены проверками некорректных и слишком длинных DNS-имён для текущих фиксированных буферов. Старое ожидание `DNS_ANS_CHECK_NOT_END_ERROR` не переносилось буквально: после Answer по стандарту могут идти Authority и Additional. Вместо этого проверяется корректная обработка пакета с Additional OPT и ожидаемым маршрутом.
